# 私聊回复执行检查

`qqbot_reply_guard` 处理规划器明确准备回应、却没有调用 `reply` 的漏执行。复制 `config.example.toml` 为本机 `config.toml`，启用 `[plugin].enabled`，确认 `[guard].bot_qq` 对应当前实例。主人账号读取 `qqbot_identity` 本机配置。

插件只检查主人的已有 QQ 私聊，且最近消息必须仍由主人发送、已出现在本轮规划上下文中。同一条新主人消息第一次进入规划时等待 2 秒，给连发补充留出时间；期间有新消息时交给原生中断流程重新收集上下文。后续围绕同一消息调用工具不重复等待。规划提示要求把连续消息作为一轮理解，由模型决定回应、等待或保持安静，避免逐条回答。规划前增加工具执行提醒；规划后已有函数调用或平台原生活动时，保持原输出。只有纯文本规划、目标尚未回复时，才用现有 `planner` 模型对这份规划核对一次动作，最长等待 15 秒。明确需要回应时补上单个原生 `reply` 调用，沿用原生回复器、人设、发送拆分和延时，引用关闭。

核对不重新策划话题。规划决定保持安静或核对不能确定意图时保持原结果。同一消息在插件进程内只核对一次，失败或超时记录日志，不循环重试。核对前后都重新确认最近消息，发现新消息或机器人已经回复时丢弃旧动作；群聊和机器人已回复后的主动续聊不受影响。

原生回复工具仍可能调用失败或生成失败，本插件不重发已有工具调用。动作核对仍依赖模型理解，不能保证所有无工具输出都能修复。正常回复不增加模型请求；触发核对时会增加一次规划模型调用及其耗时。核对调用的 token 使用由框架按本插件请求记录，原始 Planner 的 token 统计保持原值。

在本机 `bot_config.toml` 的 `[chat.reply_timing]` 中设置 `planner_interrupt_max_consecutive_count = 10`，允许新消息打断正在运行的 Planner，并在原生静默窗口结束后重新收集消息。`0` 表示禁用打断。连续打断达到上限后该次请求正常完成。此配置不取消已经进入 Replyer 或发送阶段的任务，也不能撤回已经发送的消息。

Planner 和待回复私聊的 Replyer 都追加联网工具说明：`tool_search` 查找本地延迟加载工具，规划器再调用 [qqbot_web_search](../qqbot_web_search/README.md) 提供的 `web_search` 取得官网检索证据。回复依据实际结果和来源链接，未查询时不声称已联网。执行检查插件本身不提供搜索服务、不强制每轮联网。

本轮主人消息含普通引用时，通过 `message.get_by_id` 读取同会话的原文，最多展开三个引用、每条 2000 字，不递归、不请求二进制媒体。原文、发送者角色、原消息时间及截断状态作为历史资料分别进入 Planner 和 Replyer，避免只看到 ID 后误用合并转发工具。没有取得原文则明确标记缺失。记忆规则区分检索被过滤、失败和无结果，要求不凭空补写共同经历；最终表达仍取决于模型。

使用公开 `maisaka.planner.before_request` / `after_response`、`maisaka.replyer.before_request` Hook、Context Item schema 1，以及配置、聊天流、消息查询和 `llm.generate_with_tools` 能力。插件没有直接发送消息的权限，不修改用户配置中的提示词，不持久化聊天内容，不注册后台调度。日志仅记录核对开始、保留结果、丢弃过期结果、补齐调用及错误类型。
