# 私聊原生回复与执行检查

`qqbot_reply_guard` 为已核验的主人私聊补充回复执行规则、搜索与记忆依据，并展开同会话普通引用。公开答复使用原生 `reply`：Planner 决定回应内容，Replyer 结合完整人设、说话风格、表达习惯和聊天上下文生成正文，再经过原有后处理分段和发送管线。普通答复与研究中的阶段答复使用同一条原生流程。

复制 `config.example.toml` 为本机 `config.toml`，启用 `[plugin].enabled`，确认 `[guard].bot_qq` 对应当前实例。主人账号读取 `qqbot_identity` 本机配置。

复杂问题已有可靠且有用的部分结论时，可以先调用 `reply`，在 `reply_reference` 中说明已确认事实和本次仅需回应的部分；随后继续查询或研究，有新增证据后补充。依赖工具结果的结论必须等待实际结果。简单聊天正常回答，不机械报进度，不重复已有内容，内部分析保持隐藏。查询失败时区分已有结论和缺失证据，只有新线索、不同核验方法或可恢复的临时错误才继续尝试。

原生回复成功后，由原发送管线保存消息、同步 Maisaka 历史并触发原有记忆写回；附件、共享休息状态和既有发送 Hook 继续生效。[qqbot_reply_timing](../qqbot_reply_timing/README.md) 仅调整发送等待：后处理完成后的首段补等 `max(0, 第一段原有等待 - 本轮已耗时)`，后续分段及研究补充按原速度发送。质量与耗时维护要求见根 `docs/model-routing.md` 的“回复耗时排查”。

执行检查只处理主人的已有 QQ 私聊，且最近消息仍由主人发送、已经出现在本轮规划上下文中。同一条新主人消息第一次进入规划时等待 2 秒，给连发补充留出时间；期间有新消息时交给原生中断流程重新收集上下文。同一来源的后续工具轮次不重复等待。连续消息由模型作为一轮表达理解，决定回应、等待或保持安静。

规划后已有函数调用或平台原生活动时，保持原输出及全部附件参数。只有纯文本规划且目标尚未回复时，才用现有 `planner` 模型对这份规划核对一次动作，最长等待 15 秒。明确需要回应时补上单个原生 `reply`，正文仍由原生回复器生成，引用关闭。静默、意图不明确、目标已变化或核对失败时保留原结果。同一来源在插件进程内只核对一次，超时和取消也不循环请求。群聊和已回复后的原生续轮保持原处理。

在本机 `bot_config.toml` 的 `[chat.reply_timing]` 中设置 `planner_interrupt_max_consecutive_count = 10`，允许新消息打断运行中的 Planner，并在原生静默窗口结束后重新收集消息。`0` 表示禁用；连续打断达到上限后本次请求正常完成。此设置不取消已经进入 Replyer 或发送阶段的任务，也不能撤回已发送消息。

Planner 和待回复私聊的 Replyer 都追加联网说明：`tool_search` 查找本地延迟加载工具，规划器再调用 [qqbot_web_search](../qqbot_web_search/README.md) 的 `web_search` 取得官网证据。只有实际返回的结果可作为联网依据，普通聊天不强制搜索。记忆规则区分检索被过滤、报错和无结果，不凭空补写共同经历。

本轮主人消息含普通引用时，通过 `message.get_by_id` 读取同会话原文，最多三个引用、每条 2000 字，不递归或请求二进制。原文、发送者角色、时间及截断状态作为历史资料进入 Planner 和待回复的 Replyer；缺失时明确标记未取得。

插件使用公开 Planner / Replyer 请求 Hook、Context Item schema 1 和配置、聊天流、消息查询、`llm.generate_with_tools` 能力，不注册消息发送工具。日志仅记录动作核对状态和错误类型，不输出内部推理或聊天正文。

回归验证：使用本机 Python 执行 `-m unittest discover -s pytests -p test_qqbot_public_replies.py -v`，覆盖原生工具保留、附件及研究续轮、来源核验、单次漏执行修复、静默和失败边界。测试截获能力出口，不连接 QQ 或模型。
